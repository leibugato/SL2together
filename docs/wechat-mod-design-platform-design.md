## 1. 项目背景

《杀戮尖塔 2》的 MOD 内容通常包含卡牌、遗物、事件、角色、先古之民、替换皮肤、怪物、Boss、语音替换和 Buff 等类型。玩家能够提出大量创意，但设计想法与游戏现有接口、模型体系、场景资源、音频资源和多人兼容性之间存在明显的信息差。

当前主要问题包括：

1. 玩家有想法，但不清楚是否能够实现，也不清楚需要改动哪些游戏系统。
2. 设计描述散落在聊天群、文档和社交平台，缺少可检索、可追踪的归档。
3. MOD 开发者需要反复解释相同的基础问题，沟通成本高。
4. AI 可以直接给出判断，但如果缺少结构化输入、游戏接口知识库和结果约束，容易出现过度自信或格式不稳定的问题。
5. 游戏版本更新后，原有 MOD 接口可能变化，历史评估需要标记有效版本。

本项目希望建立一个轻量的云端工具，让用户可以提交设计想法，并在需要时获得基于游戏架构的初步实现难度判断，以便修改设计、补充信息或进入实际开发。

## 2. 产品目标

### 2.1 核心目标

1. 用户可以快速创建、保存和提交 MOD 设计想法。
2. 用户可以按需触发 AI 可行性评估，而不是每次保存都消耗模型调用。
3. AI 结果以“简单、中等、困难、极难”四档为核心，同时提供原因、风险、缺失信息和调整建议。
4. 用户可以查看自己的历史提交、评估状态、评估版本和修改记录。
5. 系统尽可能减少开发与运维复杂度，首版不依赖自建服务器。

### 2.2 非目标

首版不包含以下内容：

1. 不承诺 AI 评估结果绝对准确。
2. 不自动生成可直接编译的完整 MOD 代码。
3. 不自动修改或上传游戏文件。
4. 不提供公开社区广场、点赞、评论和打赏。
5. 不代替 MOD 开发者进行最终的接口验证、平衡性测试和版本兼容测试。
6. 不处理游戏破解、绕过付费、侵权资源分发或违反游戏服务条款的内容。

### 2.3 成功指标

首版上线后重点观察：

| 指标 | 目标 |
| --- | --- |
| 开始填写到提交成功的转化率 | 大于 60% |
| 提交后触发 AI 评估的比例 | 大于 40% |
| AI 评估成功返回率 | 大于 95% |
| AI 结构化输出校验通过率 | 大于 98% |
| 用户查看历史记录的周活跃比例 | 大于 30% |
| 评估结果被用户认为“有帮助”的比例 | 大于 70% |

## 3. 用户与使用场景

### 3.1 目标用户

| 用户类型 | 主要诉求 |
| --- | --- |
| MOD 创意玩家 | 记录想法，判断是否值得继续完善 |
| 小型 MOD 开发者 | 快速判断技术范围，寻找可能受影响的系统 |
| MOD 团队协作者 | 统一记录设计，保留评估历史和版本 |
| 运营或管理员 | 查看内容状态、处理违规内容和维护评估知识库 |

### 3.2 核心场景

1. 用户想到一张新卡牌，填写名称、效果和设计意图后保存为草稿。
2. 用户完成描述后主动点击“AI 可行性评估”。
3. 系统返回“中等”及评分明细，指出“需要新增自定义 Power”和“需要补齐动态变量描述”。
4. 用户根据建议补充信息后重新评估，最终选择“提交保存”。
5. 用户以后在小程序“我的提交”中查看旧想法、历史评估和调整记录。

## 6. 功能设计

### 6.1 登录与用户身份

推荐直接使用微信小程序云开发身份体系。

流程：

1. 小程序启动时调用 `wx.cloud.init`。
2. 调用云函数 `user.bootstrap`。
3. 云函数从运行上下文读取 `OPENID`，不信任客户端传入的用户 ID。
4. 如果 `users` 集合不存在该用户，则创建最小用户记录。
5. 客户端只接收业务所需的用户资料，不接收其他用户数据。

优点：

1. 不需要账户密码。
2. 不需要自行维护微信登录会话。
3. 每条数据库记录可以绑定 `_openid`。
4. 云函数可以强制校验记录归属。

如果后续迁移到自建后端，再改为：

`wx.login -> 服务端 code2Session -> 自建会话令牌`

首版不建议引入账号密码，因为会增加注册、找回密码、撞库防护和合规成本。

### 6.2 设计表单

字段定义：

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| 内容类型 `type` | 是 | 卡牌、遗物、事件、角色、先古之民、替换皮肤、怪物、Boss、语音替换、Buff |
| 名称 `name` | 是 | 1 至 60 个字符 |
| 描述与设计 `designText` | 是 | 15 至 5000 个字符，描述玩法、触发时机和预期体验 |
| 资源链接 `resourceUrl` | 否 | 单个 URL，可指向美术或音频资源，首版最多 1 条 |
| 设计补充 `extra` | 否 | 按类型显示可选项，例如卡牌费用、遗物稀有度、角色机制 |

首版可以让 `extra` 保持轻量，正式实现时按类型动态渲染 2 至 5 个补充字段：

| 类型 | 可选补充字段 |
| --- | --- |
| 卡牌 | 费用、卡牌类型、目标、稀有度、升级变化 |
| 遗物 | 稀有度、获得方式、触发时机 |
| 事件 | 出现章节、选项数量、奖励或惩罚 |
| 角色 | 核心资源、初始牌组、起始遗物、机制关键词 |
| 先古之民 | 所属章节、遗物选项数量、对话规模 |
| 替换皮肤 | 替换对象、资源规模、是否改动场景或动画 |
| 怪物 | 出现章节、体型、行为模式、意图数量、场景与动画 |
| Boss | 所属章节、阶段数、血量与核心机制、遭遇池、场景与音乐 |
| 语音替换 | 替换角色、台词数量、触发范围、语言、音频格式 |
| Buff | 增益或减益、叠加方式、持续时间、触发时机、图标 |

补充字段不参与首轮必填校验，但可以显著提高 AI 评估质量。

### 6.3 保存草稿

行为：

1. 校验类型、名称和描述的最低要求。
2. 保存为 `DRAFT`。
3. 保存成功后可继续编辑。
4. 草稿修改后不自动触发 AI 评估。
5. 对同一记录的连续保存使用防抖和版本号，避免重复写入。

### 6.4 保存并评估

行为：

1. 完整校验表单。
2. 保存最新设计版本，保持为 `DRAFT`。
3. 创建 `EVALUATION_JOB`。
4. 立即返回 `evaluating` 状态，前端展示进度。
5. 云函数异步调用 AI 评估管线。
6. 完成后只更新独立评估状态和结果，不改变设计是否已提交。
7. 失败时保留设计正文，允许用户重试。

按钮建议：

1. `保存草稿`
2. `保存并评估`
3. `确认提交`

评估与提交解耦。用户可以先评估，再返回修改，也可以不评估直接提交。提交后再次修改会生成新版本，旧评估保留但标记为过期。

### 6.5 AI 评估结果

结果至少包含：

| 字段 | 说明 |
| --- | --- |
| 难度 `level` | 简单、中等、困难、极难 |
| 分数 `score` | 0 至 100，内部用于排序和校准 |
| 置信度 `confidence` | 0 至 1，提示结果可靠程度 |
| 摘要 `summary` | 一段面向用户的解释 |
| 实现简述 `implementationBrief` | 通俗说明评估器推测的主要实现方式，不要求用户选择代码方案 |
| 主要原因 `reasons` | 3 至 6 条 |
| 主要风险 `risks` | 0 至 5 条 |
| 调整建议 `suggestions` | 1 至 5 条 |
| 缺失信息 `missingInformation` | 仅记录会影响玩法目标、范围或可行性、且用户能从设计层回答的信息 |
| 技术依据 `technicalAnchors` | 关联到的模型、命令、池或补丁点 |
| 评估版本 `catalogVersion` | 对应游戏接口知识库版本 |

当信息不足时，仍返回一个“暂定难度”，同时显著提示“补充信息后可能变化”。这样既满足四档结构，也避免用户把不确定结果当成最终结论。

### 6.6 历史提交

列表默认按 `updatedAt` 倒序。

每条记录展示：

1. 类型标签
2. 名称
3. 当前状态
4. 最近评估难度
5. 最后更新时间
6. 是否存在未评估修改

支持筛选：

1. 全部类型
2. 草稿、已提交、评估中、已评估、评估失败
3. 简单、中等、困难、极难

详情页支持：

1. 查看设计最新版本。
2. 查看历史评估。
3. 复制设计文本。
4. 编辑并生成新版本。
5. 删除记录。
6. 重新评估。

### 6.7 修改与评估失效

设计正文修改后，已有评估结果不能继续代表最新设计。

规则：

1. 为 `submissions` 增加 `contentVersion`。
2. 每次实质性修改后 `contentVersion + 1`。
3. 评估记录保存其评估时的 `contentVersion` 和 `contentHash`。
4. 如果二者与当前提交不一致，列表和详情显示“设计已修改，评估已过期”。
5. 评估缓存键使用 `contentHash + catalogVersion + promptVersion + modelVersion`。

## 7. 数据设计

### 7.1 集合划分

| 集合 | 用途 |
| --- | --- |
| `users` | 用户基础信息与偏好 |
| `submissions` | MOD 设计主体和当前状态 |
| `evaluations` | 每次 AI 评估的不可变结果 |
| `evaluation_jobs` | 异步任务状态、重试和用量控制 |
| `catalog_versions` | 游戏接口知识库版本 |
| `usage_daily` | 用户每日调用次数与成本控制 |

```json
  "status": "QUEUED",
  "attempts": 0,
  "maxAttempts": 3,
  "lockedAt": null,
  "errorCode": null,
  "errorMessage": null,
  "createdAt": "serverDate",
  "updatedAt": "serverDate"
}
```

任务状态：

`QUEUED -> RUNNING -> SUCCEEDED`

失败路径：

`RUNNING -> RETRYING -> RUNNING`

最终失败：

`RUNNING -> FAILED`

### 7.6 `catalog_versions`

用于记录评估依据，不允许 AI 每次自行假设游戏接口。

```json
{
  "_id": "sts2-api-2026.09-r4",
  "gameBuild": "game-build-or-patch-label",
  "sourceType": "curated_reference",
  "summary": "包含 CardModel、RelicModel、EventModel、AncientEventModel、MonsterModel、PowerModel、命令、池、音频和打包规则",
  "status": "ACTIVE",
  "createdAt": "serverDate"
}
```

## 8. 技术架构

### 8.1 推荐架构

```text
微信小程序客户端
  |
  | wx.cloud.callFunction
  v
CloudBase 云函数
  |
  +--> 用户与会话校验
  +--> 表单校验与内容安全检查
  +--> submissions / evaluations 数据库
  +--> evaluation_jobs 任务队列
  +--> AI 评估服务
         |
         +--> 规则评估器
         +--> 接口知识库检索
         +--> 大模型结构化调用
         +--> JSON Schema 校验与降级
```

### 8.2 前端

| 技术 | 说明 |
| --- | --- |
| 原生微信小程序 | 兼容性和审核路径最直接 |
| TypeScript | 统一枚举、表单和评估结果类型 |
| 微信基础组件 | 首版优先使用原生组件 |
| UI 组件库 | 可选 TDesign 小程序版，不强制引入 |
| 状态管理 | 首版用页面级状态和轻量 store |

首版不建议使用跨端框架，因为项目只面向微信小程序，跨端会增加构建和调试复杂度。

### 8.3 后端

推荐使用微信云开发：

| 能力 | 用途 |
| --- | --- |
| 云函数 | 登录、校验、数据库写入、AI 调用 |
| 云数据库 | 用户、提交、评估和任务数据 |
| 云存储 | 后续上传作品图或报告图时使用 |
| 定时触发器 | 清理超时任务、重试失败任务 |
| 环境变量 | 保管 AI API Key 和模型配置 |

AI API Key 只能存储在云函数环境变量或密钥管理中，不能写入小程序代码、数据库公开字段或 Git 仓库。

### 8.4 云函数接口

| 云函数/动作 | 用途 | 关键校验 |
| --- | --- | --- |
| `user.bootstrap` | 创建或读取用户 | 使用上下文 `OPENID` |
| `idea.create` | 新建草稿或直接提交 | 字段长度、类型、归属 |
| `idea.update` | 更新设计并生成新版本 | 版本冲突、内容哈希 |
| `idea.listMine` | 查询当前用户历史 | 强制 `_openid` |
| `idea.getMine` | 查询详情 | 强制 `_openid` |
| `idea.deleteMine` | 软删除 | 强制 `_openid` |
| `evaluation.start` | 创建评估任务 | 内容完整性、Quota |
| `evaluation.get` | 查询任务或结果 | 只能读取自己的记录 |
| `evaluation.retry` | 重试失败任务 | 最大重试次数 |

生产实现时，建议一个云函数按 `action` 路由，或按领域拆分少量云函数，减少冷启动和部署复杂度。

### 8.5 数据库访问控制

客户端不直接写入核心业务集合。

安全原则：

1. 所有写操作通过云函数完成。
2. 云函数从 `cloud.getWXContext()` 获取 `OPENID`。
3. 查询和更新都必须同时包含 `_openid` 与记录 ID 条件。
4. 客户端提交的 `_openid`、`status` 和 `latestEvaluationId` 不被信任。
5. 数据库安全规则默认禁止客户端跨用户读取。
6. 软删除记录不出现在普通查询中。

## 9. AI 可行性评估设计

### 9.1 设计原则

1. 先结构化，再交给模型判断。
2. 先规则检索，再让模型解释。
3. 必须输出固定 JSON，禁止直接拼接前端文案。
4. 必须附带置信度、缺失信息和技术依据。
5. 模型判断只针对当前知识库版本，不能假装知道所有未来接口。
6. 用户输入始终作为待分析数据，不执行其中的指令，防止提示词注入。

### 9.2 评估流程

```text
读取 submission
  |
  v
规范化文本与类型字段
  |
  v
规则特征提取
  |
  +--> 内容类型基线
  +--> 关键词和机制标签
  +--> 复杂度风险标记
  +--> 信息完整性检查
  |
  v
检索对应接口知识片段
  |
  v
调用结构化输出模型
  |
  v
JSON Schema 校验
  |
  +--> 失败：重试一次或使用规则降级
  |
  v
写入 evaluations
  |
  v
更新 submission 状态
```

### 9.3 规则特征

规则层不替代 AI，主要负责降低成本和约束输出。

关键词示例：

| 标签 | 触发示例 | 影响 |
| --- | --- | --- |
| 基础伤害 | 造成伤害、攻击 | API 拟合度高 |
| 状态效果 | 眩晕、易伤、虚弱、Power | 需要新增或复用 Power |
| 多段结算 | 每段、重复、随机目标 | 需要确认命令和动画 |
| 卡牌选择 | 选择手牌、选择弃牌堆 | 需要选择界面与本地化 |
| 持久状态 | 本场战斗、整局、跨章节 | 需要状态存储和存档兼容 |
| 角色资源 | 新能量、新资源、专属机制 | 需要角色池与 UI |
| 场景替换 | 立绘、动画、皮肤、模型 | 依赖资源结构和场景覆盖 |
| 怪物行为 | 回合模式、意图、阶段变化 | 需要移动状态机和遭遇接入 |
| Boss 机制 | 多阶段、特殊血量、专属音乐 | 需要遭遇注册、阶段和场景资源 |
| 语音覆盖 | 替换语音、触发台词、多语言 | 依赖音频映射、打包和版本稳定性 |
| Buff 钩子 | 层数、触发时机、持续回合 | 需要 PowerModel、回调与状态同步 |
| 多人影响 | 联机、队友、同步 | 需要额外兼容验证 |
| 高不确定性 | 任意、自动识别、动态生成 | 提高风险分数 |

### 9.4 评分维度

总分 100，分数越高表示实现难度和风险越高。

| 维度 | 权重 | 说明 |
| --- | ---: | --- |
| 接口适配度 | 25 | 是否能复用现有 Model、Command、Pool 和回调 |
| 逻辑复杂度 | 20 | 触发条件、状态机、多段结算和交互复杂度 |
| 集成范围 | 15 | 涉及注册、池、章节、角色、存档等多个系统 |
| 美术、音频与界面 | 15 | 卡面、图标、立绘、场景、动画、语音和选择界面 |
| 兼容与稳定性 | 15 | 多人模式、存档、平衡、本地化和版本变化 |
| 不确定信息 | 10 | 描述缺失、需求模糊或可能依赖私有实现 |

规则引擎先给出各维度参考分，AI 可以调整，但必须给出原因。

### 9.5 难度分档

| 总分 | 难度 | 用户解释 |
| ---: | --- | --- |
| 0 至 24 | 简单 | 大概率可以复用现有模板和命令，主要工作集中在配置、文本和美术 |
| 25 至 49 | 中等 | 需求明确时可以完成，但需要新增部分逻辑或补充资源 |
| 50 至 74 | 困难 | 涉及多个系统、复杂状态或较大美术工作量，需要专门开发和测试 |
| 75 至 100 | 极难 | 依赖未确认接口、跨系统改动或高风险兼容问题，建议先做技术验证 |

如果 `confidence < 0.55`，前端仍展示四档结果，但标题必须显示“暂定难度”，并优先展示缺失信息。

### 9.6 类型评估基线

基线只作为规则预判，不作为最终结论：

| 类型 | 典型范围 | 主要复杂度来源 |
| --- | --- | --- |
| 卡牌 | 简单至中等 | 效果组合、动态变量、选择界面、升级 |
| 遗物 | 简单至中等 | 触发钩子、Pool、图标和描边 |
| 事件 | 中等 | 多页面、选项、奖励、章节补丁和背景图 |
| 角色 | 困难至极难 | 卡池、遗物池、药水池、资源 UI、立绘和平衡 |
| 先古之民 | 困难 | 对话、遗物选项、章节随机池、场景和美术 |
| 替换皮肤 | 中等至极难 | 替换范围、场景结构、动画和游戏更新兼容性 |
| 怪物 | 中等至困难 | 行为状态机、意图、数值、场景与章节遭遇接入 |
| Boss | 困难至极难 | 多阶段机制、遭遇池、平衡、场景、音乐和专属表现 |
| 语音替换 | 简单至极难 | 台词数量、触发映射、语言覆盖、音频格式和版本兼容 |
| Buff | 简单至困难 | 叠加方式、触发钩子、持续规则、图标和状态同步 |

### 9.7 结构化输出

模型必须返回类似以下结构，前端只消费通过校验的数据：

```json
{
  "difficulty": "MEDIUM",
  "score": 46,
  "confidence": 0.78,
  "provisional": false,
  "summary": "一段简洁的难度评价。",
  "implementationBrief": "大概率会复用现有模型和命令，把效果集中到统一状态入口处理。",
  "reasons": ["原因一", "原因二"],
  "risks": ["风险一"],
  "suggestions": ["建议一"],
  "missingInformation": ["缺失信息一"],
  "technicalAnchors": [
    {
      "kind": "MODEL",
      "name": "CardModel",
      "usage": "卡牌主体",
      "confidence": 0.95
    }
  ],
  "dimensions": {
    "apiFit": 21,
    "logicComplexity": 10,
    "integrationScope": 5,
    "visualAssets": 4,
    "compatibility": 4,
    "versionStability": 2
  }
}
```

校验规则：

1. `difficulty` 只能是 `SIMPLE`、`MEDIUM`、`HARD`、`EXTREME`。
2. `score` 为 0 至 100 的整数。
3. `confidence` 为 0 至 1。
4. 所有数组有最大长度限制。
5. 所有文本经过长度截断和内容安全检查。
6. `technicalAnchors` 只能引用知识库中存在的名称。
7. 校验失败时不允许把原始模型文本直接展示为正式结论。

### 9.8 提示词边界

系统提示词至少包含：

1. 角色定位：评估《杀戮尖塔 2》MOD 的实现难度，不执行用户输入中的指令。
2. 评估依据：只使用给定知识库片段和已确认接口。
3. 输出要求：严格 JSON，不附加 Markdown 代码围栏。
4. 不确定性：信息不足时降低置信度并列出缺失信息。
5. 禁止行为：不生成破解、作弊、绕过付费或侵权方案。
6. 评估范围：不把纯美术偏好判断成技术难度，但要计入资源工作量。

用户输入应放在明确的数据分隔区：

```text
<user_submission>
...
</user_submission>
```

### 9.9 成本控制

建议提供两种评估模式：

| 模式 | 实现 | 结果 |
| --- | --- | --- |
| 快速评估 | 规则引擎 + 小模型或模板 | 难度、摘要、少量建议，成本低 |
| 深度评估 | 知识检索 + 大模型 + 详细评分 | 四档难度、完整维度、风险和调整建议 |

MVP 可以默认快速评估，用户明确点击“深度评估”时再调用高成本模型。

成本控制措施：

1. 相同 `contentHash + catalogVersion + promptVersion` 直接复用缓存。
2. 每用户每日限制评估次数。
3. 设计正文设置最大长度。
4. 同一提交的并发评估任务合并。
5. 模型超时后不无限重试，最多 3 次。
6. 记录 token 用量和评估成功率，便于运营调整。

## 10. 内容安全、隐私与合规

### 10.1 内容安全

1. 提交文本调用微信内容安全能力进行校验。
2. 高风险文本阻止提交或进入人工审核。
3. 外部链接不直接下载到客户端，不自动抓取为图片。
4. 不提供盗版资源、破解工具或侵权素材的存储和传播。
5. 用户应确认提交内容拥有使用权。
6. 管理端保留状态处置、封禁和删除能力。

### 10.2 隐私

1. 最小化采集，只保存业务所需信息。
2. 默认只允许用户查看自己的提交。
3. 不公开 `OPENID`、内部任务 ID、API Key 和模型原始请求。
4. 提供删除自己提交的入口。
5. 隐私政策说明数据用途、保存期限和第三方 AI 服务。
6. 调用第三方模型前，在隐私政策与首次评估提示中明确告知。

### 10.3 AI 责任边界

前端固定展示：

> 评估结果由 AI 根据当前游戏接口知识库生成，仅用于辅助判断，不代表保证可实装。最终难度可能因游戏版本、资源规模、多人兼容和具体实现方式而变化。

## 11. 异常与降级

| 异常 | 处理 |
| --- | --- |
| 微信登录失败 | 保留本地草稿，提示重试 |
| 网络中断 | 草稿本地暂存，恢复后同步 |
| AI 超时 | 任务标记 `RETRYING`，允许稍后查看 |
| AI 返回非 JSON | 重新请求一次，仍失败则使用规则模板结果 |
| 模型服务不可用 | 允许切换到备用模型或仅保存提交 |
| 内容安全接口失败 | 阻止高风险提交，普通文本可降级为人工队列 |
| 游戏知识库版本过期 | 标记结果“可能过期”，提示重新评估 |
| 用户超额 | 展示剩余次数和下次可用时间 |
| 重复点击评估 | 使用幂等键与任务锁避免重复调用 |

## 13. 验收标准

### 13.1 P0 功能验收

1. 微信用户首次进入后自动获得唯一用户记录。
2. 用户可以创建十种类型的设计。
3. 必填校验、长度限制和错误提示符合设计。
4. 用户可以保存草稿并再次编辑。
5. 用户可以保存并评估，也可以不评估直接确认提交。
6. 评估中、成功、失败三种状态均可见。
7. AI 成功返回时包含四档难度、摘要、原因、风险或建议。
8. 模型输出不合规时不会污染正式评估结果。
9. 用户可以查看自己的历史提交和评估记录。
10. 用户不能读取或修改其他用户的数据。
11. 修改设计后旧评估会显示为已过期。
12. 删除后普通列表不再显示该记录。

### 13.2 技术要求

1. 核心云函数输入均做服务端校验。
2. API Key 不出现在客户端包和日志中。
3. 评估任务具备幂等、超时和重试机制。
4. 数据库查询有分页。
5. 评估结果按固定 Schema 校验。
6. 关键错误能在云开发日志中定位到提交 ID，但不泄露完整隐私内容。

### 13.3 体验要求

1. 表单在主流手机宽度下无横向滚动。
2. 长文本、长按钮和四档标签不溢出。
3. 评估中状态有明确反馈，不需要用户反复点击。
4. 历史列表可以快速识别草稿、评估失败和评估过期。
5. AI 结论先显示难度摘要，技术细节按需展开。

## 16. 当前需要确认的产品决策

以下问题不阻塞首版开发，但会影响后续实现：

1. 历史提交是否默认私密，还是允许用户主动公开。
2. 是否同时提供快速评估和深度评估，还是首版只保留一种。
3. 是否允许用户上传美术资源到云存储，还是首版只接收外部链接。
4. AI 服务提供商、模型和预算上限。
5. “替换皮肤”是否需要区分贴图替换、立绘替换、动画替换和完整场景替换。
6. 游戏接口知识库由谁维护，以及更新频率。
7. 是否需要公开分享评估结果图。
8. “语音替换”是否允许上传完整音频包，还是只接收资源链接和替换说明。
9. “怪物”和“Boss”是否共用一套详情字段，还是 Boss 独立增加阶段和遭遇配置。
10. “Buff”是否只包含战斗内 Power，还是也包含遗物、事件等来源施加的长期状态。
